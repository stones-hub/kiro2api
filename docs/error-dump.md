# 错误现场记录与后台查看

## 目标
请求出错时保存这次请求的完整现场：客户端请求、发给 Kiro 的请求、Kiro 的响应，各含头和体。在管理后台“错误日志”页点开查看，可分段复制，也可一键复制全部，方便排查问题。

## 配置
`KIRO_ERROR_DUMP`，启动时读取：
- 未设置或为空：开启（默认）。
- `off`（忽略大小写和首尾空白）：关闭，不写文件，后台页面显示“已关闭”。
- 其他值：启动失败退出，防止写成 `false`、`0` 却以为已经关了。

只在管理模式（`KIRO_ADMIN_DATA_DIR`）下生效，文件写在数据目录下的 `error-dumps/` 里。不在管理模式时不记录。

## 什么时候记录
一次失败的尝试写一条。换号重试时，第一次失败也会写，并标注“已换号重试”：
1. Kiro 返回非 200。
2. 连不上 Kiro，包括网络错误和账号代理错误。
3. Kiro 返回 200，但流里出现 `exception` 或 `error` 事件（流式、非流式、OpenAI 入口都算）；非流式响应解析失败也算。
4. 没有可用账号、请求转换失败。这两种情况没有上游部分，只记录客户端请求。

客户端自身的问题不记录：请求体不是合法 JSON、模型不存在、参数校验失败、客户端主动断开。

## 每条记录的内容
- 摘要：时间、类型、request_id、尝试次数及是否已换号重试、账号（ID 和邮箱）、模型、是否流式、上游状态码、返回给客户端的状态码、错误说明。
- 客户端请求：方法、路径、全部请求头、原始请求体。
- 发给 Kiro 的请求：URL、全部请求头、请求体（经过转换和 system 清洗之后的版本）。
- Kiro 响应：状态码、全部响应头、响应体。流中途出错时记录那条异常事件的完整内容，以及出错前已读取的字节数和事件数。

限制：
- 流中途出错时，记录不到完整的原始字节流。
- 请求体、响应体每段最多保留 2 MiB，超出部分截断，并注明原始大小。
- 目录里只保留最新 200 条，旧的自动删除。

## 安全
- 请求头里的密钥打码，只保留前 4 位和后 4 位，长度不足的整段打码。打码的字段有：`Authorization`、`X-Api-Key`、`Cookie`、`X-Kiro-Admin-Token`、发给 Kiro 的 `Bearer` token。完整密钥不会写进文件，也不会在页面上出现。
- 请求体和响应体以明文保存用户对话。文件权限 0600，目录权限 0700，只能通过管理后台查看。
- 写文件失败只打一条警告，不影响请求本身。

## 后台
- 左侧菜单“使用日志”下面新增“错误日志”。列表按时间倒序（北京时间），列出时间、类型、状态、账号、模型、request_id，每行有“查看”按钮。
- 点“查看”打开详情弹窗，分“客户端请求 / 发给 Kiro / Kiro 响应”三段。JSON 自动格式化，内容过长时在框内滚动。每段一个“复制”按钮，底部一个“复制全部”按钮。复制的是完整原文，不截断显示。
- 接口：`GET /api/error-dumps` 返回列表，只有摘要；`GET /api/error-dumps/:id` 返回单条完整内容。两个接口都走管理后台现有的鉴权和来源校验，id 严格校验格式，防止路径穿越。
- 主日志里对应的错误日志行增加 `error_dump` 字段，值为这条记录的 id。

## 验证
- 单元测试：四类错误各写一条且内容完整；换号重试时两条记录及标注正确；打码；截断；只保留 200 条；`off` 不写；非法配置启动失败；客户端问题不记录；列表和详情接口；非法 id 被拒绝。
- 本机候选：用真实路由 + 假上游制造各类错误，检查生成的文件；再用独立测试浏览器打开后台，验证列表、详情弹窗和复制功能。

## 实现说明
- 代码：`server/error_dump.go`（记录、打码、截断、保留、管理接口），测试 `server/error_dump_test.go`；页面在 `static/admin/` 的「错误日志」。
- 文件：`<数据目录>/error-dumps/<id>.json`，id 形如 `20261029-073045-123-002a9f3c`（UTC 时间到毫秒 + 4 位进程内序号 + 4 位随机数，按名排序即按时间排序），接口只接受这个格式。文件以 `summary` 开头，列表只读摘要，不读请求体。先写临时文件再改名，写完删掉超出 200 条的最旧记录。
- 接入点：`buildCodeWhispererRequest` 记下发给 Kiro 的请求（引用，不复制）；`attemptCodeWhispererRequest` / `inspectUpstreamResponse` 在非 200、网络错误、代理错误、转换失败时生成记录，挂在 `upstreamFailure` 上，由 `executeCodeWhispererRequest` 在确定是否换号后写出；流式 `processEvent`、OpenAI 流式循环、两个非流式处理函数记录 `exception` / `error` 事件和解析失败；`acquireRequestAccount` 记录没有可用账号。成功请求只在 context 里多存几个引用，不写文件。
- 主日志：`上游响应错误`、`读取错误响应失败`、`账号代理连接失败`、`发送请求失败`、`请求转换失败`、`构建请求失败`、`上游失败，换号重试一次`、`上游失败且没有其他可用账号，返回原始错误`、`非流式解析失败` 增加 `error_dump` 字段。新增三行日志：`没有可用账号`（Warn）、`上游响应中出现异常事件`（Warn）、OpenAI 非流式的 `非流式解析失败`（Error），都带 `error_dump`。
- 启动日志一行说明开启（含目录）、关闭或非管理模式。
- 日志里出现过的 id 都能解释：记录生成后若因客户端已断开而没有保存，打一条 Info `客户端已断开，未保存错误现场`（带 `error_dump`）；写盘失败打 Warn `错误现场写入失败`（带 `error_dump`）。
- 类型（`kind`）：`upstream_status` 上游返回错误、`upstream_unreachable` 连不上上游、`proxy_error` 账号代理错误、`stream_exception` 响应中的异常、`parse_error` 响应解析失败、`no_account` 没有可用账号、`conversion_error` 请求转换失败（客户端 400）、`build_error` 请求构建失败（序列化或创建请求失败，客户端 500）。

### 与上文的细节差异
- 打码：短于 12 字节的值整段换成等长 `*`；另外也打码 `Proxy-Authorization` 和 Kiro 响应里的 `Set-Cookie`。`Bearer` / `Basic` 前缀保留。
- 不是合法 UTF-8 的请求体/响应体以 base64 保存并标注 `body_encoding: base64`（非流式响应是 AWS 二进制事件流，通常属于这种）；异常事件另存为解码后的 JSON（`event` 字段），页面优先看它。
- 换号重试前的那条记录 `client_status` 为空（这次失败没有返回给客户端），页面显示「已换号重试」。
- “没有可用账号”只记 `ErrPoolUnavailable`（503）；并发已满（429，`ErrPoolBusy`）和排队时客户端离开不记录。
- 流中异常的“已读取事件数”按读到异常所在的那块数据为止统计，可能包含同一块里异常之后的事件。
- 功能关闭时详情接口返回 404，列表返回 `enabled: false`。
- `ContentLengthExceededException`（及类型含 `CONTENT_LENGTH_EXCEEDS` 的异常）不记录、不打异常日志：网桥把它当作 `max_tokens` 正常截断返回，客户端看到的不是错误。判断与流式处理里映射为 max_tokens 的条件是同一个函数（`maxTokensException`），流式、非流式、OpenAI 入口一致。
- 异常事件（`event`）同样受单段 2 MiB 上限：序列化后超出时改存截断后的 JSON 文本，标注 `event_truncated` 和原始大小 `event_bytes`。
- `error` 事件的说明在 `error_code` / `error_message` 为空时退回嵌套的 `error.message` 或 `raw_data.message`。
- 代理错误的说明用 `utils.ProxyErrorMessage` 生成（如“代理拒绝连接，请检查地址和端口”），记录里不出现代理地址和凭据；主日志 `账号代理连接失败` 行保持原样。
- 写入时顺带删除目录里异常退出残留的 `.dump-*.tmp`。

### 已知限制
- WebSearch 路径（`/v1/messages` 只带原生 web_search 工具）、流式中途读取上游失败、非流式读取 200 响应体失败不在上述四类内，不记录。
- 解析器很宽松，正常情况下非流式“解析失败”几乎不会出现；这一分支只有单元测试，没有端到端测试。
- 记录同步写盘，只发生在失败路径上，成功请求不写盘。会让请求本身等待的写盘有两处：换号重试前写第一次失败的记录（推迟重试发出），以及流内异常在转发给客户端之前写记录（推迟这条异常事件的转发）；其余记录在错误响应写给客户端之后才写。磁盘很慢时这两处会相应变慢。
- 磁盘预算：单条记录最多三段请求体/响应体各 2 MiB、异常事件 2 MiB，非 UTF-8 响应体存 base64 约 2.7 MiB，常见最坏约 9 MiB，200 条约 1.8 GB。JSON 会转义控制字符（`\u00XX`，一个字节变 6 个），若内容全是控制字符，单条理论上限约 50 MiB、200 条约 10 GB；实际错误请求多为几十 KB 到几 MB。
- 时钟回拨：id 以系统时间开头，按名排序即按时间排序。时钟回拨后新记录会排在旧记录前面，列表顺序错乱，而且清理时可能先删掉新记录。不处理。
